# Changelog

All notable changes to shulker are documented here. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- `init` creates a `shulker.json` manifest; `add`, `remove`, `update`, `outdated`, `pin` and `unpin` manage mods, with exact versions and hashes recorded in `shulker.lock`. `--as` gives an entry a key of your own, recorded against the jar's own mod id, and a key another entry already holds is refused rather than taken over.
- Dependency problems found in jar metadata fail the command that would lock them and print the `shulker ignore` line that accepts each one; `unignore` drops it again. An ignore records the range the jar declared, so a new version that declares something else brings the problem back.
- `lock` brings `shulker.lock` in line with hand edits to `shulker.json` and changes to local packs without upgrading anything, and the out-of-date warning names each difference.
- A `requires` entry can name a local jar or zip with `file`, locked by its sha512 and placed like any other mod, resource pack or shader. `add ./my-mod.jar`, `resourcepack add` and `shader add` take a path: a file inside the project is referenced where it lies, and one outside it is copied into `files/`, which builds, installs and overrides leave alone. `list` shows a local entry's path in place of a version, `update` and `outdated` skip it, and `pin` and `unpin` refuse it. `pull` adopts a jar or pack named in a build directory's `mods/`, `resourcepacks/` or `shaderpacks/` as such an entry rather than an override, with `--as` for a key already taken, and gives an adopted pack whose name isn't `<key>.zip` that name as its `filename`, so the next build places it where it was rather than beside it and it stays enabled. `export curseforge` matches a local file by fingerprint like any other, and `export mrpack` ships one inside the archive with `--bundle`.
- A resource pack or shader's `file` can name a folder of the pack's sources: `lock` zips it, leaving out dot files, `Thumbs.db`, `desktop.ini`, `*~` and `*.swp` and following symlinks with a warning, and locks and places the zip like a local zip, so the same folder gives the same bytes on every machine. Editing a file in the folder makes the lock out of date. `add`, `resourcepack add` and `shader add` take such a folder: one inside the project is referenced where it lies, and one outside it is copied into `files/`. A folder the game or Iris wouldn't load, with no valid `pack.mcmeta` or no `shaders/` at its root, is still locked, with a warning naming what is missing.
- `set`, `unset` and `get` edit and read any field of `shulker.json` by dotted path, checked against the schema before anything is written. `get --locked` reads `shulker.lock` the same way, so a release workflow can take the exact Minecraft version and loader from it.
- A `shulker.json`, `shulker.lock`, `shulker.local.json`, `config.json` or `registry.json` that doesn't parse is reported with its line and column and what was expected there, and a manifest or lock that doesn't match its schema lists each failing field by dotted path.
- A `shulker.json` written by a newer shulker fails `schema-newer` in one sentence and says to run `shulker self update`, and one naming a `$schema` this shulker doesn't know fails `manifest-invalid` naming it. One with no `$schema` loads as the current version and gains the line the next time shulker saves it.
- `config get|set|unset` read and change shulker's own `config.json`: the CurseForge key, masked unless `--reveal`, and where the registry lives, which needs `--force` when linked instances would be left behind.
- Fabric, Quilt, NeoForge and Forge projects (`init --loader`); on Quilt, mods without a Quilt build use their Fabric one.
- NeoForge and Forge servers and launcher profiles set up by the loader's own installer: servers run it offline from files recorded in `shulker.lock`, and `link mojang` installs the client into the official launcher without leaving the installer's own profile behind.
- Mods from Modrinth and CurseForge, with provider fallthrough, manual downloads for files CurseForge won't serve, and `add --provider` to switch a locked mod.
- CurseForge works without your own API key: release builds include one, and if CurseForge rejects it shulker fetches a replacement from shulker.sh.
- Dependency checks from each jar's own metadata on `add` and `install`; `remove` prunes dependencies nothing else needs. A `fabric.mod.json` or `quilt.mod.json` with a raw newline or tab inside a string reads as Fabric and Quilt read it.
- `add` holds every version already in the lock and resolves only what is new, so adding one mod never quietly upgrades the rest. A mod that needs another version of a held dependency stops the add and names what would have to move; `--with-deps` moves them, and a dependency a locked modpack pins is listed in `shulker.json` as it moves, so it no longer follows the modpack. On a terminal the add asks `Move it?` instead of stopping, and a project with no loader asks which one to use and carries on.
- `suggests` lists the mods locked mods recommend and that aren't installed; `--optional` adds their optional integrations. A mod named by the Modrinth or CurseForge slug of one already locked, like `yacl` for YACL's `yet_another_config_lib_v3`, is listed as installed under its key, and `add` no longer reports it missing.
- A project declares its sides as blocks, `"client": {}` and `"server": {}` in `shulker.json`; `install` and `build` build every declared side into `build/<side>`, `build <side>` and `diff <side>` name one, and `sync --side` picks one for a source. A side whose `build` is `.` builds into the project directory itself, leaving `shulker.json`, `shulker.lock`, `shulker.local.json`, `.shulker/` and the data directories alone and making no data links. Override folders follow a convention rather than a list: `overrides/` for both sides, `client-overrides/` and `server-overrides/` for one, and `<feature>-overrides/` (or the path a feature declares) while that feature is on, later folders winning. `pull` puts a file back in the folder that holds it, `overrides/` for a new one, or the folder `--to` names. `sync` and `export` take `--assume-client` to build a client from what both sides share when the manifest declares none. Adding a mod that ships only on a side the project doesn't declare warns and names the `shulker set` line that ships it on both, unless it came in as a dependency or sits behind a feature or OS condition.
- Override folders never put `.DS_Store`, `._*` AppleDouble files, `Thumbs.db` or `desktop.ini` into a build or an export, and a local modpack does not count as changed when one appears. `skipFiles` in `shulker.json` leaves out more by glob: a glob with no slash matches a file name at any depth. `pull` skips a named file that builds leave out.
- `history list|show|prune` and `rollback [n]` for instances: an entry is kept before anything changes — by `add`, `remove`, `update` and `lock` before they rewrite `shulker.json` and `shulker.lock`, and by an in-place build before it writes over config or overrides you edited — holding the manifest, the lock, `config/` and every other managed file, with mods left to the cache. `show` names what restoring an entry would do to the mods, resource packs and shaders it holds, and `rollback` keeps the current state as an entry of its own before restoring and building. Only `prune` deletes: the manifest's `history` number is the depth it trims to and the count a build warns above, with `-1` keeping everything and `0` taking none.
- `cache info` and `cache prune` report and trim the downloads shulker shares between projects. Everything a registered instance or the project you are in references is kept — its lock, the lock of every history entry it keeps, the lock of the git or URL checkout it was built from, and the modpack checkouts and offline fallbacks their sources need — and the rest goes, with the managed Java runtimes left alone. A registered folder that is gone is skipped; one whose lock can't be read stops the prune instead of guessing, while `cache info` still reports and names it. Nothing shulker placed leaves a build directory without its bytes reaching the cache first, so a rollback still works offline. `--lock` keeps a named lock file's files too, so a CI runner with no registered instances can prune a cache shared by several packs.
- Server builds with the locked server jar, `eula.txt` and validated `server.properties`; `serve` runs them on Mojang's Java runtime.
- A `sync` that can't reach one of a project's git or URL modpacks keeps that modpack at the version in `shulker.lock` and warns, while the other modpacks still update and the sync succeeds, so `sync --offline` works in an in-place project and one unreachable modpack no longer makes a pre-launch sync give up the rest.
- `server.resourcePack` names a locked resource pack for joining clients to download: a server build writes its URL and sha1 as `resource-pack` and `resource-pack-sha1`. A feature on the pack's entry decides whether it is pushed and the build says when one doesn't; an `os` doesn't. A key that isn't a locked resource pack, a local file, a pack its provider won't redistribute, or either key also set by hand fails the build, and a pack over 250 MiB warns. `pull` leaves the two keys out of the manifest.
- `player` resolves names against Mojang and writes the whitelist, ops and bans.
- `client.options` merges into `options.txt`, and `.properties` and other owned files merge per key, so in-game edits survive a rebuild; `diff` and `pull` bring them back into the project. A `.properties` override nothing merges into is placed exactly as written, line endings and all.
- `client.optionsPath` writes `client.options` and the seeded resource pack list somewhere other than `options.txt`, in builds and exports alike, such as `config/modpack_defaults/options.txt` for Config Manager to copy into place only where a player has none.
- Per-side data directories linked into builds, so worlds, logs and screenshots survive rebuilds.
- `link shulker` makes an instance shulker owns, under its own instances root, and `play` launches it with no other launcher involved: it syncs the instance, unless `--no-sync` or the instance's `hooks.preLaunch` is off, resolves the account, fetches the Minecraft version, libraries, assets and loader into a shared store (a download line for each), and starts the game detached, with its output in a log file in the instance. A watcher shulker starts in the background records how the run ended, and `--wait` or `--stream` keep the launch in the foreground instead. `--world` and `--server` boot straight into a save or a server through the game's quick play, `--window` sets the size for one run, and `--dry-run` shows what a launch would assemble without an account. Once a launch has filled the store, the next one works offline. NeoForge and Forge packs run the loader's installer against the store, and Fabric and Quilt packs take their loader from its own metadata. The session token is never printed or logged.
- `accounts` lists the accounts a launch can use, grouped as your own, offline and borrowed, each with its id and whether it can play, and marks the default. `accounts login` signs in to Microsoft with a code shown in the terminal, asking for no more than Xbox sign-in and offline access, and renews the session on its own before a launch; `logout` signs out, `add` and `remove` create and delete offline accounts once an account that owns Java Edition is in sight, `use` picks the default, and `refresh` renews your own accounts and re-reads borrowed ones. Accounts are named by username or id, or the start of either, optionally as `name@source`; the closest of several matches is chosen with a warning, and accounts the input can't tell apart open a picker on a terminal. `accounts providers` orders where accounts are read from — shulker's own `accounts.json`, Prism Launcher's accounts, and the Minecraft Launcher's — and shulker never renews or writes another launcher's accounts.
- `instance get|set|unset|edit` read and change one instance's settings. `memory`, `jvmArgs`, `java`, `window` and `wrapper` take their defaults from `play.` keys in `config.json`, which an instance's own value overrides, and `account` pins the account an instance plays as. `config set --literal` sets a list or an object from JSON, such as `accounts.providers`.
- Save groups share worlds between the instances shulker launches itself: each instance's `saves/` links to group `default` under the saves root, a junction on Windows, and `settings.savesGroup` picks another group or `none`, relinking on the next sync without copying or merging anything. `saves` lists the groups, or one group's or instance's worlds and backups; `saves prune --keep <n>` trims the backups; `play.saveBackups` in `config.json` is how many automatic backups to keep. `backup` zips a target's worlds into its backups, and `restore [n]` puts one back, or any zip of world folders `--backup` names, replacing each world it holds whole after backing up what was there. `--world` narrows either to the worlds it names, and `restore --as` puts a single world back under another name, which is how one server's world goes into a server with a different `level-name`. `update`, `sync` and the sync before a launch back up the worlds first whenever the mods change, and keep only the `play.saveBackups` newest of those automatic backups; one `backup` or `restore` took is never trimmed. `restore` refuses a world open in a running game, since the game would write it back over the restore, and backing one up warns that the zip may be torn. `saves`, `saves prune`, `backup` and `restore` take `--all`, `--launcher` and `--side` as `sync` does, acting on each save group once, and `saves` shows the Minecraft version and loader each backup was taken on.
- `modpack add|remove|list` layers other projects in from local paths, git repositories or manifest URLs, each keyed by the name in its own manifest unless `--as` says otherwise. A modpack that ships a `shulker.lock`, beside the manifest for a URL, is locked by default: its exact versions are copied in, dependencies included, and its Minecraft and loader must match, or are taken from it when `shulker.json` sets none of its own and every locked modpack agrees; `--unlocked` resolves its mods here instead, and a mod you list yourself always wins. On a terminal, a locked modpack built for another Minecraft asks whether to unlock it. `--no-auto-update` keeps a modpack where it is on `sync`, while `update` still moves it. A modpack's own `file` entries resolve in its directory or git checkout and are cached when the consumer locks, so one its author never committed still builds from the cache; a manifest URL carries no files, so a `file` entry there is refused.
- A modpack can be a local `.mrpack`: `modpack add ./cozy.mrpack`, or a bare `add`, writes a `file` entry, copying an archive from outside the project into `files/`. Its mods lock as the modpack's, found by hash on Modrinth or reused from the shulker project the archive carries, and the files neither knows or that project had as local files, with its three override folders, are laid by the modpack before your own overrides. The archive is locked by its sha512 and kept in the cache: changing it makes the lock out of date until `lock` reads it again (`autoUpdate: false` holds it until `update`), a deleted one builds from the cache with a warning, and `cache prune` keeps it. An unlocked archive's mods relock from the lock alone until its bytes change, and a lookup that fails, offline or not, names the file. A CurseForge modpack zip is taken the same way, by `modpack add ./craft.zip` or a bare `add` that finds its `manifest.json`: each file locks by its CurseForge project and file ID, a file its author won't let CurseForge serve locks as a manual download from `downloads/`, and its overrides folder is laid by the modpack. Reading one needs the network even when every file it names is cached, so doing so offline fails with `curseforge-offline`; a locked one that hasn't changed still builds offline. A file that isn't a modpack archive is refused by its content.
- A modpack can be a Modrinth or CurseForge modpack by its slug: `add cozy`, or `modpack add cozy`, writes a `type: modpack` entry naming the provider and project and locks the newest version that fits the project's Minecraft and loader, or the newest overall for a project that sets neither, which then takes the pack's platform. That version's archive is consumed as a local one is and kept in the cache, so a locked pack builds offline and `cache prune` keeps it. `pin`, `unpin`, `update` and `outdated` treat it like a mod, `sync` never moves it, `list` shows its version, and `--ref`, `--unlocked` and `--no-auto-update` are refused with the reason each doesn't apply.
- `resourcepack add|remove|list` and `shader add|remove|list` manage resource packs and shaders, and the provider's own project type decides what an entry is, so plain `add` usually needs no `--type`. Each is placed under its `requires` key, `resourcepacks/<key>.zip` or `shaderpacks/<key>.zip`, rather than the provider's file name, so one you enabled in game stays enabled when it updates. The lock records the shader mods each shader is tagged for, and a build enables the first shader that an Iris or Oculus it placed can load, through that mod's own config; a local shader loads in either. The shader mod is found by its jar id among the mods the build placed, so one behind a feature, renamed with `--as` or from CurseForge is found too. Every other placed shader gets a line in the build report saying how to turn it on: in game, in Canvas's own menu, or, when nothing in the build can load it, `shulker add iris`. A shader that ships vanilla core shaders is placed and enabled as a resource pack instead. The enabled list in `options.txt` is seeded once and then left to you. An entry's `filename` places it under a name of your own, and a renamed pack keeps its place in the enabled list. A pack from Modrinth or CurseForge is locked with its sha1 too: the provider's own, or one computed from the download when the provider gives none.
- Mods gated on OS or a named feature; `feature on|off|reset|list` saves per-machine choices in `shulker.local.json`, and `--with`, `--without` and `--os` override them for one run.
- A ModMenu entry with the pack's name, version, description, authors and links, which badges managed mods and turns off their update checks; NeoForge and Forge packs get the same summary in the mod list.
- `sync` builds one side of a local project, git repository or manifest URL into any directory, and falls back to the last successful sync when the network is down (`--offline` skips the network). Inside an instance, a project that builds into its own directory, `sync` fetches the modpacks that follow their source, relocks without moving your own mods and builds in place, then syncs every instance built from it; a launch builds what the lock already has when that update fails. `update` in an instance builds in place too, and names `shulker sync` when instances are built from it, since it leaves them to `sync`.
- `link prism`, `link multimc`, `link atlauncher`, `link gdlauncher` and `link mojang` (alias `vanilla`) create instances or profiles for the client build; a Prism, ATLauncher or GDLauncher instance syncs before each launch, and ATLauncher and GDLauncher need no clicks to set one up, NeoForge and Forge included, and show the pack's `icon`, or the shulker image, until you pick your own; a later change to the pack's icon replaces it. Every `link` takes a project directory, git URL, or manifest URL, so a pack can be played without a project of your own, and makes the instance a project in its own right: a `shulker.json` in the launcher's game directory that follows the source as a modpack, takes its Minecraft version, loader, features and overrides from it, and builds in place before `link` returns. `shulker add` there puts a mod on top of the pack and keeps it through every update. The pack's `history` and `marker` settings are copied once and are the instance's own from then on, and a pack with no client block still builds from what it shares, with a warning. `link` adopts a project it finds in the game directory rather than writing over it, and `--force` repoints the modpack it follows while keeping what you added. `link mojang` keeps its game directories under `shulker/` in the launcher folder.
- A bare `link` on a terminal asks which launcher to link, and `link multimc` asks where MultiMC is installed. A `link` with no source outside a project asks what `init` would and makes the instance a project of its own, or follows the pack you name.
- `instances` lists the instances shulker keeps in sync, each under a short id of its own; `-i <id>` acts on one from anywhere, and `--as` picks the id when a `link` creates it. `sync -i`, `sync --all` and a picker update them, and a bare `sync` inside a project updates just that project's instances; `unlink` stops syncing one, named by its id, by the name its launcher shows, by directory or, inside a project, by launcher (`unlink mojang`), and leaves the project whole, so a later `link` picks it back up. An instance's `.shulker/instance.json` holds the settings that decide how shulker sets it up; a `sync --into` directory is a detached build with no registry row, and records there what it syncs from as well. Inside a project, a bare `sync` lists its detached builds too, marked `detached build` with their directory (`"detached": true` in the JSON), each under an id taken from its folder name that `sync -i` takes there, suffixed only when a registered instance already holds it. `instances repair` rebuilds the registry from what the launchers and shulker's own instances root hold, recognising an instance by its `shulker.json` even when its `.shulker/` is gone and giving it back the id it was linked under and the name its launcher shows, follows a rename made in the launcher while keeping the id, and writes any instance file that has gone missing.
- Prism, ATLauncher and GDLauncher instances run shulker through a small script in their own `.shulker/` folder rather than a command shulker wrote into the launcher, so an update before each launch keeps working when the binary moves, and a failure never stops the game starting. A command already in the launcher's slot is adopted rather than replaced: it is kept in the instance's own settings, still runs first, and `unlink` puts it back. Each hook can be turned off per instance in `.shulker/instance.json`, and how each run ended is recorded in `.shulker/launches.json`, capped by `settings.launchHistory`.
- The official launcher keeps a linked profile fresh too. It runs no commands of its own, so `link mojang` points the profile's Java at a small shim shulker generates in the instance's `.shulker/` folder: it hands the launch to shulker, which syncs the instance and then starts the game with shulker's managed Java runtime, and runs the recorded Java directly when shulker is gone, so a deleted binary costs updates rather than the game. The profile's own Java setting is put back when the hooks are turned off, on `unlink` and on `self uninstall`. On macOS and Linux the shim is a shell script; on Windows it is an executable shulker compiles with the C# compiler Windows ships, falling back to a copy of itself, and reads the two paths it needs from a file beside it. A launch that can't start is never silent: it says why in the launcher's own game output and exits with an error, so the launcher raises one too rather than closing on you with no window and no message. That covers an instance file shulker can't read, no Java recorded, and a Java that won't run, the last two also leaving a record of a launch that never happened, which `instances` and `.shulker/launches.json` both show. A launch that is going ahead never raises one: a sync that fails warns and the game starts on what is already there, and a `settings.wrapper` that won't run gives way to Java on its own.
- Every `link` takes `--no-hooks`, `--no-pre-launch`, `--no-post-exit`, `--no-marker`, `--with-marker`, `--java <path>` and `--wrapper <cmd>`, which seed the new instance's own `settings`; the manifest's `client.hooks` are the defaults a flag overrides, and after the link the instance file decides and no sync writes over it. The marker is layered rather than seeded: `settings.marker` decides for an instance that sets it, `--no-marker` and `--with-marker` are what write it, and while it is absent the manifest's `marker` decides, so the same manifest gives the same build every time no matter how often it has been synced. `settings.marker` off drops the ModMenu entry from a build, `settings.java` is the Java this machine launches with, and `settings.wrapper` is written into Prism's, ATLauncher's and GDLauncher's own wrapper setting, or put in front of the Java command by the Mojang shim, only when you set one.
- Every sync records when it ran and how it ended, in the instance's own `resolved` block and in the registry, so `instances` shows a stale or failing instance rather than only what is on disk. A failed sync keeps the time of the build that is actually there.
- `init` with no loader on the client side, and `install` on a client project nothing is linked or synced from yet, end by pointing at `shulker link <launcher>`.
- `self uninstall` takes shulker back out: it removes the hooks, scripts, slots and shim from every instance and puts each official launcher profile's own Java back, then removes the binary. Instance folders and the registry stay, so reinstalling and running `instances repair` puts it all back; `--purge` forgets the registry too. Nothing prompts, and an instance it can't unhook is a warning rather than a stop.
- `export mrpack` and `import mrpack` for Modrinth modpacks.
- `export curseforge` writes a CurseForge profile `.zip` the CurseForge app imports. Mods from Modrinth or a URL are matched to CurseForge files by fingerprint, and a Modrinth file whose fingerprint misses is matched to the CurseForge file with its slug, name and size when the two unpack to the same contents; `--bundle` ships the ones that aren't on CurseForge inside the archive. A resource pack or shader that goes in by file ID is enabled under CurseForge's file name, which is what the launcher saves it as. Its `modlist.html` links each project's CurseForge page and reads `<name> (by <author>)`, and every file carries `isLocked: false`, as the CurseForge app writes them.
- `export mrpack` and `export curseforge` take a project directory, git URL or manifest URL to export from, with `--ref`. Any source downloads the locked files its exported sides use and the cache lacks, so a fresh checkout exports without `install`.
- Both exports carry resource packs and shaders alongside the mods, as client-only files, and write the project's own `shulker.json` and `shulker.lock` at the archive root, so importing an exported pack restores the project it came from even when that project has no loader and so ships no marker jar. The manifest's `icon`, a PNG in the project, goes in as `icon.png` at the root of an mrpack, which the Modrinth App shows, and as the CurseForge profile image; without one the shulker icon does. A manifest with `marker` off leaves them out, along with the shulker icon, so the archive carries nothing of shulker's own. `import mrpack` reads those in preference to the marker jar and puts locked resource packs and shaders back as entries, and the icon back at the path the manifest names, and a local file the pack bundled becomes the new project's own in `files/`; `--ignore-shulker` skips them and imports the archive as any other Modrinth modpack.
- `--json` on every command: one envelope with the result, every warning and, on failure, a stable error code; the codes are listed in the CLI reference, and the plain error line ends with the same code.
- JSON Schemas for `shulker.json` and `shulker.lock` at `https://shulker.sh/schema/v1/`.
- Human output with one style throughout: green, yellow and red `+ ~ -` change lines, `✔` and `!` result lines, an error tree under `✘ error:` with the code, steps that spin while they run, say how long they have waited and on which host once they are slow, and settle into grey `✔` lines, a download bar on terminals that fills by bytes with sizes recorded in `shulker.lock`, paths that click where the terminal supports links, and `--help` in the same style with the commands grouped by task, opening with each command's description and examples from the CLI reference. A usage error prints the command's usage line and flags under it. `--no-color` (or `NO_COLOR`) and `--ascii` turn colour and the Unicode glyphs off.
- Installers for macOS and Linux (`curl -fsSL https://shulker.sh/install.sh | sh`) and Windows (`irm https://shulker.sh/install.ps1 | iex`), and `self update`, all checking releases against their SHA256 checksums and, when `gh` is installed, their build provenance.
- `completion bash|zsh|fish|powershell` prints a shell completion script, and the CLI reference shows how to load it in each shell.
- `search` finds projects on Modrinth and CurseForge and prints the ids to add them by; with no words it opens a search box whose results follow what you type.
- A bare `add` on a terminal opens the same search box, where you mark as many results as you like and add them all at once.
- `init` on a terminal asks what you are making, which Minecraft version, whether to add mods, which loader and which version of it, and whether to start from an existing pack, each starting on the default its flag has, so taking them all creates what `--yes` creates. `--no-input` asks nothing anywhere and takes every default, which output that isn't going to a terminal and `--json` imply; `init --yes` is its alias on that command. Every question is a picker you can leave with esc, including the ones that already existed: which instance to sync, which account, and the EULA.
- `docs` prints the documentation built into the binary, so it matches the installed version and works offline: a page, a command's section, or any heading, with a list to pick from when several match, and `--search` finds a phrase on every page.
- Every run that writes a file or starts the game appends to `log.jsonl` beside `config.json`, even when it has nothing to do: when it started and ended, with its flags, instance and exit code, the result `--json` would have printed, whether or not it was asked for, and every warning and error it showed. A command that changes nothing, like `list`, `get` or `version`, is logged only when it warns or fails, and then without its result. Progress lines are never logged. The file is readable only by you, and never holds the game's arguments `hook wrap` hands on, which carry the session token. Each run that writes to it trims it: entries older than `log.keepDays` in `config.json` go, 30 days without it, and past 4 MiB the oldest go whatever their age. `shulker log` shows the last 24 hours of it under a line naming the shulker version, the platform and the filter, so a slice pasted into an issue explains itself, and `--since`, `--group`, `--cmd`, `--code`, `--level` and `-i` narrow it. What it prints is redacted, safe to paste into an issue: credentials in a URL, CurseForge keys and your home directory are hidden, and `--unredacted` shows the entries as stored.
- `log` shows what shulker did over the last day, filtered by `--since`, `--group`, `--cmd`, `--code`, `--level` and `-i`, under a preamble naming the shulker version, the platform and how many entries matched, so a pasted slice explains itself.
- `import curseforge` creates a project from a CurseForge modpack zip, locking each file by its project and file ID and taking the pack's overrides as the project's own. Files CurseForge won't serve are all named in one error, and lock as manual downloads once they are in the project's `downloads/`. A zip that isn't a CurseForge modpack is refused by its content. A zip shulker exported comes back as the project it came from, as with `import mrpack`: each file matched by its bytes returns as that project locked it, a bundled local file becomes the new project's own, and `--ignore-shulker` skips all that.

### Changed
- `.shulker/state.json` records `side` in place of `target`. A state file from an earlier build decodes with an empty side, so the next build treats that directory as fresh and writes everything again; there is no migration.
- The marker jar, both exports and the Quilt server launch jar are zipped the same way on every machine and Go release: deflated by a pinned compressor with fixed timestamps and entries in path order, so the same project gives the same bytes wherever it is built. The Quilt launch jar is now compressed, so a lock that recorded the old one fails with `lock-stale` once the jar leaves the cache; remove `loader.server` from `shulker.lock` to relock it.
